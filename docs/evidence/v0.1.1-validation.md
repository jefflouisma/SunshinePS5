## Pad ownership finding

A non-shipping probe (`tools/ps5-probes/pad_census.c`) lists registered virtual pads by writing
a neutral report to each candidate handle. Handles on 13.60 look like
`(sequence << 16) | (kind << 8) | slot`. A second probe (`tools/ps5-probes/pad_fdpass.c`) showed:

- a pad is removed when the last reference to the `/dev/hid` open file that registered it is
  closed (process exit included);
- passing that descriptor to another process with `SCM_RIGHTS` keeps the pad registered after the
  creator exits (30 s of accepted reports, then a clean removal by the receiver);
- AF_UNIX sockets bind under `/system_tmp`; `/data` and `/user/temp` refuse them (`EOPNOTSUPP`).

| Creator host → new build | `takeover descriptor_received=true reused_handle=1901327`; creator exited | 1 | 0 |
| Official client session without gamepad, then teardown | pad still registered | 1 | 0 |
| Takeover again → controller session | same handle `1901327`; CON-input **Pass** | 1 | 0 |
| v0.1.1 release build takeover | `descriptor_received=true reused_handle=1901327` | 1 | 0 |

The three resident processes visible on the test console (from v0.1.0 and earlier diagnostic
builds) predate this change; they hold no pads and disappear at the next reboot.
